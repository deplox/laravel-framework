# Opinionated Laravel Framework Fork

This document is the single source of truth for every deliberate divergence between this fork (`deplox/laravel-framework`, branch `13.x-opinionated`) and the upstream `laravel/framework`. It is written for three audiences simultaneously: **human developers** reading top-to-bottom, **AI coding assistants** (Claude Code, Copilot, etc.) doing a quick structural lookup, and **engineers migrating** an existing Laravel app onto this fork.

## Overview

This is an opinionated fork of the Laravel framework that enforces a set of structural and behavioural conventions the Deplox team considers better defaults. It stays in sync with upstream `laravel/framework` via regular merge commits; the opinionated commits sit on top.

To use this fork in a Laravel application, add a `vcs` repository entry and a `require` override in `composer.json`:

```json
{
    "repositories": [
        {
            "type": "vcs",
            "url": "https://github.com/deplox/laravel-framework"
        }
    ],
    "require": {
        "laravel/framework": "dev-13.x-opinionated"
    }
}
```

The downstream application skeleton must be updated alongside the framework. Generated files land in different directories than stock Laravel, so the skeleton's base classes (especially `app/Controllers/Controller.php`) must exist at the new paths. The [migration checklist](#migrating-an-existing-laravel-app-to-this-fork) below covers each required adjustment.

## Detailed Changes

### 1. Flattened `App\` namespace layout

**What changed.** The default namespace for five generator commands has been simplified by removing the `Http\` and `Console\` nesting prefix. Everything that was inside `App\Http\` or `App\Console\` is now directly under `App\`.

| Generator | Old default | New default |
|---|---|---|
| `make:controller` | `App\Http\Controllers` | `App\Controllers` |
| `make:middleware` | `App\Http\Middleware` | `App\Middleware` |
| `make:request` | `App\Http\Requests` | `App\Requests` |
| `make:resource` | `App\Http\Resources` | `App\Resources` |
| `make:command` | `App\Console\Commands` | `App\Commands` |

**Why.** HTTP concerns no longer monopolise the app directory. Middleware, requests, and resources are usable outside a web context; grouping them under `Http\` implied otherwise.

**Code paths.**
- `src/Illuminate/Routing/Console/ControllerMakeCommand.php:100` — controller default namespace
- `src/Illuminate/Routing/Console/ControllerMakeCommand.php:231` — request namespace when `--requests` flag is used
- `src/Illuminate/Routing/Console/MiddlewareMakeCommand.php:66`
- `src/Illuminate/Foundation/Console/RequestMakeCommand.php:64`
- `src/Illuminate/Foundation/Console/ResourceMakeCommand.php:93`
- `src/Illuminate/Foundation/Console/ConsoleMakeCommand.php:76`
- All 13 controller stubs at `src/Illuminate/Routing/Console/stubs/controller*.stub` — `use` line changed from `use {{ rootNamespace }}Http\Controllers\Controller;` to `use {{ rootNamespace }}Controllers\Controller;`

**Framework consumers also updated.**
- `ApplicationBuilder::withCommands()` defaults to `app_path('Commands')` (was `Console/Commands`).
- `RouteListCommand::formatActionForCli()` strips `App\Controllers\` prefix from action display names.
- `TransformsToResource::guessResourceName()` resolves to `App\Resources\…`.
- `DownCommand` imports `App\Middleware\PreventRequestsDuringMaintenance`.

**What is NOT changed.** Models (`App\Models`), Notifications, Policies, Mail, Jobs, Events, Listeners, Observers, Rules, Casts, Channels, Providers, Exceptions — all remain at their stock defaults.

**Effect on a downstream app.** `php artisan make:controller Foo` creates `app/Controllers/Foo.php`. The downstream app skeleton must include `app/Controllers/Controller.php` (the base controller class), since all generated controllers import `App\Controllers\Controller`.

**Override.** To restore a stock path for a specific type, override `getDefaultNamespace()` in a custom artisan command that extends the relevant `MakeCommand`. At runtime there is no enforcement — you can keep files at old paths, but new generation will go to the new location.

### 2. Migrations: filenames, ULID keys, no `down()`

**What changed.** Three independent conventions were updated together:

#### 2a. Filename prefix — Unix timestamp instead of datetime

New migrations are named `<unix-timestamp>_<name>.php` (e.g. `1746280953_create_posts_table.php`) instead of the upstream `Y_m_d_His` format (e.g. `2026_05_03_142233_create_posts_table.php`).

**Why.** A 10-digit Unix timestamp is monotonically increasing regardless of timezone, server clock skew, or DST changes. Two migrations generated one second apart are unambiguously ordered.

**Code paths.**
- `src/Illuminate/Database/Migrations/MigrationCreator.php` — `getDatePrefix()` now calls `time()`
- `src/Illuminate/Console/MigrationGeneratorCommand.php:106` — existence-check glob updated to `*_create_…` (no longer requires `Y_m_d`)
- `src/Illuminate/Queue/Console/{BatchesTableCommand,FailedTableCommand,TableCommand}.php` — same glob simplification
- `src/Illuminate/Session/Console/SessionTableCommand.php:63`
- `src/Illuminate/Foundation/Console/VendorPublishCommand.php:360,365` — regex accepts both legacy `\d{4}_\d{2}_\d{2}_\d{6}_` and new `\d{10,}_` prefixes; **published filenames are rewritten to the unix-timestamp format** so vendor migrations match the fork's convention
- `src/Illuminate/Foundation/Console/ApiInstallCommand.php:130` — Sanctum migration detection regex accepts both prefixes; without this, `install:api` would re-publish the Sanctum migration on every run

**Backward compatibility.** Existing migrations with the `Y_m_d_His` prefix continue to run. The Migrator resolves class names by detecting the prefix length, and `VendorPublishCommand` handles both forms when renaming published stubs.

#### 2b. No `down()` method in stubs

All migration stubs — including user-generated migrations and every published infrastructure table — no longer include a `down()` method.

**Why.** Rollbacks in production are dangerous. Enforcing forward-only migrations as the default discourages teams from relying on `migrate:rollback` as a safety net.

**Code paths.** `src/Illuminate/Database/Migrations/stubs/{migration.stub,migration.create.stub,migration.update.stub}` — `down()` bodies removed. Same change propagated to `Cache/Console/stubs/cache.stub`, `Notifications/Console/stubs/notifications.stub`, `Queue/Console/stubs/{batches,failed_jobs,jobs}.stub`, `Session/Console/stubs/database.stub`.

**Rollback behaviour.** `Migrator::runDown()` (`src/Illuminate/Database/Migrations/Migrator.php`) detects forward-only migrations via `method_exists($instance, 'down')`. When `down()` is missing, the migration is reported as `SKIPPED` and the record is **not** deleted from the `migrations` table — otherwise the next `migrate` would re-run `up()` and typically fail with "table already exists." `migrate:rollback` is therefore a loud no-op, not a silent footgun.

**Override.** Add `down()` manually to any migration that genuinely needs rollback support.

#### 2c. ULID primary keys everywhere

All infrastructure table stubs now use ULID primary keys instead of auto-incrementing integers, UUIDs, or plain strings.

| Table stub | Old PK | New PK |
|---|---|---|
| `migration.create.stub` (user tables) | `$table->id()` | `$table->ulid('id')->primary()` |
| `notifications` | `$table->uuid('id')->primary()` | `$table->ulid('id')->primary()` |
| `jobs` | `$table->bigIncrements('id')` | `$table->ulid('id')->primary()` |
| `failed_jobs` | `$table->id()` | `$table->ulid('id')->primary()` |
| `job_batches` | `$table->string('id')` | `$table->ulid('id')` |
| `sessions` | `$table->string('id')` | `$table->ulid('id')` |

The `notifications` table also switches `morphs('notifiable')` to `ulidMorphs('notifiable')`. The `sessions` table switches `foreignId('user_id')` to `foreignUlid('user_id')` and `string('ip_address', 45)` to `ipAddress('ip_address')`.

**Code paths.** All stubs listed above in `src/Illuminate/…/Console/stubs/`.

#### 2d. `migrations` repository table

The internal `migrations` table that Laravel uses to track which migrations have run now uses a ULID PK and includes a `created_at` timestamp column.

**Code paths.**
- `src/Illuminate/Database/Migrations/DatabaseMigrationRepository.php` — `createRepository()` and `log()` updated
- `src/Illuminate/Database/Migrations/Migrator.php` — class-name resolution handles both old and new filename prefixes

**Compatibility.** The `log()` method has a try/catch fallback that inserts without `id`/`created_at` if the columns don't exist, so existing `migrations` tables continue to work — you just won't get ULID IDs or timestamps for old records. To fully migrate: add `id ulid primary key` and `created_at dateTime nullable` to your existing `migrations` table.

### 3. Authentication: column constants

**What changed.** The `Authenticatable` and `MustVerifyEmail` traits now define their configurable column names as **class constants** instead of mutable protected properties. `Foundation\Auth\User` now implements `MustVerifyEmail` by default.

**Why.** Constants are more explicit, statically analysable, and prevent accidental runtime mutation of column names.

**New constants.**

| Constant | Default value | Trait |
|---|---|---|
| `Authenticatable::EMAIL` | `'email'` | `Illuminate\Auth\Authenticatable` |
| `Authenticatable::AUTH_PASSWORD` | `'password'` | `Illuminate\Auth\Authenticatable` |
| `Authenticatable::REMEMBER_ME` | `'remember_token'` | `Illuminate\Auth\Authenticatable` |
| `MustVerifyEmail::VERIFIED_AT` | `'verified_at'` | `Illuminate\Auth\MustVerifyEmail` |

**New methods.** `getEmailName()` returns `static::EMAIL`. `getVerifiedAtName()` returns `static::VERIFIED_AT`. All auth internals (`SessionGuard`, `DatabaseUserProvider`, `CanResetPassword`, etc.) use these accessors instead of hard-coding column names.

**`Foundation\Auth\User` now implements `MustVerifyEmail`.** Every app that extends this base user model implicitly requires email verification. All users are expected to verify on signup.

**Code paths.**
- `src/Illuminate/Auth/Authenticatable.php` — constants and `getEmailName()` / `getRememberToken*()` (null-safe)
- `src/Illuminate/Auth/MustVerifyEmail.php` — `VERIFIED_AT` constant, `getVerifiedAtName()`
- `src/Illuminate/Foundation/Auth/User.php` — implements `MustVerifyEmailContract`, uses `MustVerifyEmail` trait
- `src/Illuminate/Auth/GenericUser.php` — parallel constants added

**How to override.**

```php
class User extends \Illuminate\Foundation\Auth\User
{
    const EMAIL = 'username';           // use 'username' column for auth
    const AUTH_PASSWORD = 'pass_hash';  // custom password column
    const REMEMBER_ME = null;           // disable remember-me entirely
    const VERIFIED_AT = null;           // disable email verification requirement
}
```

**Nullable vs non-nullable constants.**

| Constant | Nullable? |
|---|---|
| `EMAIL` | No — must always be a column name. To opt out of email-based auth, write a custom user provider rather than nulling the constant. |
| `AUTH_PASSWORD` | No — must always be a column name. Use a different guard if you don't want password auth. |
| `REMEMBER_ME` | Yes — `null` disables the remember-me feature entirely; `getRememberToken()` and `setRememberToken()` become no-ops. |
| `VERIFIED_AT` | Yes — `null` makes `MustVerifyEmail` a complete no-op: `hasVerifiedEmail()` returns `true` (the user is treated as already verified), `markEmailAs[Un]Verified()` no-op and return `true`, and `sendEmailVerificationNotification()` returns without dispatching. |

The property-based override (`protected $rememberTokenName = '...'`) no longer works — use constants.

### 4. Email verified column rename

**What changed.** The default email verification timestamp column is `verified_at` instead of `email_verified_at`.

**Why.** The column name `email_verified_at` is redundant on a `users` table where "verified" unambiguously refers to email. Shorter names reduce boilerplate in queries, casts, and API serialization.

**Code paths.**
- `src/Illuminate/Auth/MustVerifyEmail.php:15` — `const VERIFIED_AT = 'verified_at'`
- `src/Illuminate/Contracts/Auth/MustVerifyEmail.php` — `getVerifiedAtName()` added to contract

**Effect on a downstream app.** The `users` migration must create a `verified_at` column (not `email_verified_at`). Any `$casts`, `$fillable`, API resources, and frontend references must use the new name.

**How to override.** Declare `const VERIFIED_AT = 'email_verified_at'` on your `User` model to keep the old column name. Set to `null` to disable verification entirely.

### 5. Sessions: ULID IDs

**What changed.** Session IDs are now lowercase ULIDs instead of 40-character random alphanumeric strings.

**Why.** ULIDs are time-sortable, which improves index locality in database-backed sessions. They are shorter than UUIDs and unambiguously unique.

**Code paths.**
- `src/Illuminate/Session/Store.php` — `generateSessionId()` returns `strtolower((string) Str::ulid())`; `isValidId()` accepts both ULIDs and legacy 40-char IDs
- `src/Illuminate/Session/Console/stubs/database.stub` — schema updated (see table in [§2c](#2c-ulid-primary-keys-everywhere))
- `src/Illuminate/Session/Console/SessionTableCommand.php` — migration existence check simplified

**Backward compatibility on deploy.** `isValidId()` continues to accept legacy 40-char alphanumeric session IDs, so existing user sessions are not invalidated during a rolling deploy. New sessions created after the upgrade use ULIDs.

**Implication: `user_id` must be a ULID.** The sessions table stub uses `foreignUlid('user_id')`, which assumes the `users` table PK is also a ULID. If your users table uses integers or UUIDs, adjust the sessions migration accordingly.

### 6. `RedirectIfAuthenticated`: 403 for JSON requests

**What changed.** When an already-authenticated user hits a guest-only route (login, register, etc.) and the request is a JSON/API request (`$request->expectsJson()`), the middleware now throws `HttpException(403, 'Already authenticated.')` instead of redirecting.

**Why.** A redirect makes no sense for API/SPA clients. A 403 lets the client handle the error programmatically.

**Code paths.**
- `src/Illuminate/Auth/Middleware/RedirectIfAuthenticated.php:44-46`
- `tests/Auth/RedirectIfAuthenticatedMiddlewareTest.php` — test pinning the 403 behaviour

**Effect.** HTML clients (Blade apps) are unaffected — they still get a redirect. JSON/API clients receive a 403 JSON-parseable error response. If your SPA currently relies on catching a 302 to detect "already logged in", update it to catch 403 instead.

### 7. Authorization: `viewAny` renamed to `list`

**What changed.** The resource ability that fires when a controller's `index()` action is authorized has been renamed from `viewAny` to `list`.

**Why.** `list` is a clearer verb for "can this user see the collection?", aligning with common REST API semantics.

**Code paths.**
- `src/Illuminate/Foundation/Auth/Access/AuthorizesRequests.php:116` — `resourceAbilityMap()` maps `'index' => 'list'` (was `'viewAny'`)
- `src/Illuminate/Auth/Access/Gate.php:235` — `Gate::resource()` default abilities map
- `src/Illuminate/Foundation/Console/stubs/policy.stub:14` — generated method is `public function list(...)`

**Effect on a downstream app.** `authorizeResource(Post::class)` in a controller will call `$policy->list($user)` for the `index` route. A policy that only has `viewAny()` will receive no call and the default policy response (deny) applies. **This is a silent behaviour change** — no exception is thrown; the action simply gets unauthorized.

**How to migrate.** Rename `viewAny()` to `list()` in every policy that uses `authorizeResource()` or `Gate::resource()`. Manual calls like `$this->authorize('viewAny', Post::class)` continue to work; only the resource-wiring goes through the map.

**How to override.** Pass an explicit ability map to `authorizeResource()`:

```php
$this->authorizeResource(Post::class, 'post', [
    'index' => 'viewAny',  // keep old name for this controller
]);
```

### 8. Notifications via the facade

**What changed.** Email verification and password reset notifications are now sent through `Notification::send($user, new ...)` (the facade) rather than `$user->notify(new ...)`.

**Why.** Routing notifications through the facade allows `Notification::fake()` in tests to intercept them without needing to mock the user model or the notification driver.

**Code paths.**
- `src/Illuminate/Auth/MustVerifyEmail.php:58` — `sendEmailVerificationNotification()`
- `src/Illuminate/Auth/Passwords/CanResetPassword.php` — `sendPasswordResetNotification()`

**Effect on a downstream app.** Tests that use `Notification::fake()` will now correctly capture verification and reset notifications. Tests that mock `$user->notify()` directly may need to be updated to use `Notification::fake()` instead.

### 9. Container aliases: `'notification'` and `'broadcast'`

**What changed.** `ChannelManager` (notifications) is now bound under the `'notification'` string key, following the same convention as `'mailer'`, `'queue'`, `'cache'`, and `'log'`. `BroadcastManager` has been updated to bind under `'broadcast'` (which the container already aliased, but the provider now binds the singleton explicitly under that key).

**Code paths.**
- `src/Illuminate/Notifications/NotificationServiceProvider.php:34-47`
- `src/Illuminate/Support/Facades/Notification.php:95` — facade accessor returns `'notification'`
- `src/Illuminate/Foundation/Application.php:1664` — core aliases table entry
- `src/Illuminate/Broadcasting/BroadcastServiceProvider.php:18-40`

**Effect.** `app('notification')` now resolves. `app('broadcast')` was already registered in core aliases; the provider now consistently binds to that key. If you swap the notification manager in a service provider, bind it under `'notification'` (not `ChannelManager::class`) to ensure the facade picks it up.

---

### 10. Soft import removal (Folio, Octane)

**What changed.** `use Laravel\Folio\Folio;` and four `use Laravel\Octane\Events\…;` imports have been removed from framework files. Both packages are now referenced by fully-qualified class name inline.

**Why.** Soft `use` imports at the top of a file cause static analysers and IDEs to flag errors when the package is not installed, even when the references are guarded by `class_exists()` checks.

**Code paths.**
- `src/Illuminate/Foundation/Configuration/ApplicationBuilder.php` — Folio FQCN
- `src/Illuminate/Foundation/Exceptions/Renderer/Listener.php` — Octane event FQCNs

**Effect.** No runtime change. PHPStan, Psalm, and IDE inspections no longer produce false positives for missing Folio/Octane classes.

---

### 11. Miscellaneous small changes

- **`Env::getOption()` refactored.** `src/Illuminate/Support/Env.php:252-265` — `switch` replaced with `match`. No behaviour change; pure readability improvement.
- **`Recaller` made `readonly`.** `src/Illuminate/Auth/Recaller.php` — `recaller`/`segments` properties are `readonly`; the recaller string is parsed once in the constructor instead of on each method call.
- **`RouteListCommand` strips flattened prefix.** `src/Illuminate/Foundation/Console/RouteListCommand.php:433` — strips `App\Controllers\` (not `App\Http\Controllers\`) from action names in `route:list` output.

## Migrating an Existing Laravel App to This Fork

Work through this checklist when switching an existing standard Laravel app onto this fork.

### Composer

- [ ] Add the `vcs` repository entry pointing at `https://github.com/deplox/laravel-framework` in `composer.json`.
- [ ] Pin `laravel/framework` to `dev-13.x-opinionated` (or the specific tag).
- [ ] Run `composer update laravel/framework`.

### Directory structure

- [ ] Move `app/Http/Controllers/` → `app/Controllers/` and update all `namespace App\Http\Controllers` → `namespace App\Controllers`.
- [ ] Move `app/Http/Middleware/` → `app/Middleware/` and update namespaces.
- [ ] Move `app/Http/Requests/` → `app/Requests/` and update namespaces.
- [ ] Move `app/Http/Resources/` → `app/Resources/` and update namespaces.
- [ ] Move `app/Console/Commands/` → `app/Commands/` and update namespaces.
- [ ] Ensure a base `app/Controllers/Controller.php` exists with `namespace App\Controllers` (generated controller stubs import it).
- [ ] Update any remaining references (route files, service providers, tests) that use the old `App\Http\` / `App\Console\` namespaces.

### Database

- [ ] Rename `email_verified_at` → `verified_at` in your users migration, **or** add `const VERIFIED_AT = 'email_verified_at'` on your `User` model.
- [ ] Update `$casts`, `$fillable`, API resources, frontend code, and Eloquent queries that reference `email_verified_at`.
- [ ] If you rely on `migrate:rollback` or `migrate:refresh`: add `down()` bodies to any migration that needs to be reversible. New stubs no longer generate them.
- [ ] If you have an existing `migrations` table you want to upgrade: add `id ulid primary key` and `created_at dateTime nullable` columns (optional — the framework falls back gracefully without them).
- [ ] Review your `users` migration — if it used `$table->id()` (bigIncrements), consider switching to `$table->ulid('id')->primary()` to match the FK expectations in sessions, notifications, and other infrastructure tables.

### Authentication

- [ ] If you customised auth column names via `protected $rememberTokenName = '...'` etc., replace with class constants: `const REMEMBER_ME = '...'`. Set to `null` to disable.
- [ ] Review whether you want every user to go through email verification (`Foundation\Auth\User` now implements `MustVerifyEmail` by default). Override `const VERIFIED_AT = null` to opt out.

### Authorization

- [ ] Rename `viewAny()` → `list()` in every policy that is wired up via `authorizeResource()` or `Gate::resource()`.
- [ ] Search your test suite for assertions that a guest-only route returns a redirect for an authenticated JSON request — update to expect 403.

### Notifications & testing

- [ ] If tests mock `$user->notify()` to capture verification/reset notifications, switch to `Notification::fake()`.

### Sessions

- [ ] If you publish and use the sessions migration, re-publish it after updating the framework (`php artisan session:table`) — the schema now uses ULID PK and `foreignUlid('user_id')`.

## Source-of-Truth Diff

The exhaustive line-level diff between upstream and this fork:

```bash
git diff 13.x..13.x-opinionated
```

Or to see just the changed files:

```bash
git diff --stat 13.x..13.x-opinionated
```

Commit log for the opinionated layer:

```bash
git log --oneline 13.x..13.x-opinionated
```
